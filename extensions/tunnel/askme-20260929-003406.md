# Tunnel design interview (consolidated)

Full implementation spec: [SPEC.md](SPEC.md). Answers recorded together after the interview, as requested.

## Access and pairing

Q: (critical) Should the extension manage Tailscale Serve?
A: No. User configures Tailscale manually; extension owns only the local server.

Q: (critical) Can several devices or API clients pair?
A: Yes. Each pairs with a fresh single-use six-digit code. `/px:tunnel pair` issues another.

Q: (critical) Can every paired client view and send in the same conversation?
A: Yes; full mirroring, with the same read/write rights.

Q: (important) Must v1 render tool details?
A: Initially considered text plus working state only; later revised: include thinking, tool calls and results if straightforward. Full raw tool results, including potentially sensitive content, are allowed to paired clients.

Q: (important) What happens after five wrong pairing codes?
A: Invalidate that code; request another with `/px:tunnel pair`.

Q: (critical) How long does the code last, and does phone login persist?
A: Six digits, five minutes, single-use. A paired client remains authorized until tunnel off or Pi exit, including reconnections.

## Session lifecycle

Q: (critical) What happens when Pi switches or forks sessions?
A: Keep tunnel and pairing active; clients follow the current active session.

Q: (critical) What does the phone show after a session change?
A: Clearly indicate the change and replace the conversation with the new active branch; no browsing past sessions in v1.

Q: (important) Should `/reload` preserve the tunnel?
A: Yes, including pairing state; clients may briefly reconnect.

Q: (important) Should the phone navigate sessions?
A: Not needed in v1; desired for v2.

## Prompt delivery

Q: (critical) What can users do while Pi is busy?
A: Offer Queue, Steer, or Don't send. Queue is the default; Steer gets next-turn priority. Use Pi's native follow-up/steer behavior, not a separate queue.

Q: (critical) What happens to queued prompts on session changes?
A: Follow Pi's own terminal/native queue semantics; tunnel must not impose separate rules.

Q: (important) Can the phone cancel/reorder queued prompts?
A: Not in v1. Native optional Queue is simple; queue editing is deferred.

## API and conversation

Q: (critical) Does pairing expose conversation before tunnel activation?
A: Yes, entire current active branch, so work can continue seamlessly from phone.

Q: (important) Is an unsent terminal-editor draft synchronized?
A: No in v1; each input surface keeps its own unsent draft.

Q: (critical) How do non-browser API clients authenticate?
A: Exchange a fresh pairing code for a bearer credential; browser uses a secure cookie. Both retain full access until off/exit.

Q: (important) Should the API invent its own event/message model?
A: No. Reuse Pi's internal structures where practical; minimal versioned transport wrapper. Include thinking/tool data if simple, not filtered only for UI.

Q: (important) How should clients recover missed events?
A: Fresh active-branch snapshot plus live stream, with a gap-free transition. No durable event replay required.

## Mobile UX and operations

Q: (critical) Should phone approve terminal permission prompts?
A: No for v1; show Needs attention in Pi terminal where detectable.

Q: (important) Should phone stop current output?
A: Yes; Pi native abort, acknowledging side effects may not be undone.

Q: (important) Should v1 send photos/images?
A: No; text-only prompt submission for now.

Q: (important) Stable local port?
A: Yes, configurable fixed port; fail clearly if occupied.

Q: (critical) How do multiple Pi terminals share one port?
A: They do not in v1. V1 is one process/port. V2 adds a small separate Go gateway to provide a shared endpoint and project/session switching.
